# AutomataCLI – Enterprise Architecture & System Design Document

## 1. The Pipeline Pattern (`Illuminate\Pipeline\Pipeline`)
At the core of AutomataCLI's execution engine lies Laravel's `Illuminate\Pipeline\Pipeline`, leveraged to achieve clean separation of concerns, linear composability, and functional immutability. In standard enterprise software, process automation often degrades into monolithic, procedural service methods spanning thousands of lines, laden with nested `if/else` control flow, brittle try-catch blocks, and tightly coupled side effects. By adopting the Pipeline pattern, each discrete business process is encapsulated into an isolated, single-responsibility class adhering to `App\Nodes\Contracts\NodeInterface`. Every node implements `handle(WorkflowContext $context, Closure $next): WorkflowContext`, allowing nodes to operate as middleware wrapping the workflow execution context. Crucially, each node is resolved on demand through Laravel’s Service Container (`$container->make($nodeClass, ['config' => $nodeConfig])`), enabling full dependency injection (e.g., HTTP clients, storage drivers, and logging facilities) without polluting the workflow orchestrator. This completely decouples orchestrator logic from node domain logic and guarantees compliance with the Open-Closed Principle: introducing a new node requires zero modifications to existing pipeline orchestration.

## 2. Idempotent Execution & State-Preserving Resumption
Business process automation in enterprise environments is inherently susceptible to transient network partitions, third-party API rate limits, and external service downtime. AutomataCLI enforces strict idempotency through stateful snapshot persistence and atomic step verification across `WorkflowRun` and `WorkflowNodeExecution` models. When a workflow executes, every node is accompanied by an execution record that captures its status (`PENDING`, `PROCESSING`, `COMPLETED`, `FAILED`, `RATE_LIMITED`), attempt counter, and an immutable snapshot of both the input and output payload DTOs. If a failure or unhandled exception occurs at Step 3 (`GeneratePdfInvoiceNode`), the engine halts, commits the error summary, and leaves Steps 1 and 2 in their `COMPLETED` state while marking Step 3 as `FAILED` and preserving Steps 4 and 5 as `PENDING`. Upon invoking `php artisan automata:run {id} --resume` (or `automata:resume {id}`), the `WorkflowManager` inspects the topological node executions; any node already marked `COMPLETED` is safely bypassed. The engine restores the preserved output payload snapshot of the last completed node directly into the active `WorkflowContext` DTO and resumes execution *precisely* at the failed node. This guarantees that preceding non-idempotent side effects—such as payment authorization or database inserts—are never re-executed, while transient API rate-limit errors trigger automated exponential backoff calculations ($delay = 2^{attempt - 1} \times retry\_after$) with automatic in-process retries.

## 3. Polymorphic Node Configuration Architecture
In a heterogeneous workflow engine like Zapier or n8n, node configurations diverge radically: an `InboundWebhookNode` requires HMAC secrets, signature headers, and IP allowlists; an `ExtractCustomerDataNode` requires JSONPath mapping rules and validation flags; an `AsyncPdfInvoiceNode` requires rendering templates, page geometry, and queue targets; while an `EmailCustomerNode` requires SMTP credentials, subject templates, and MIME attachments. Storing these disparate requirements in an untyped JSON column forfeits database integrity, typed Eloquent casting, and model-level validation. AutomataCLI solves this by implementing Laravel's Polymorphic Relationships (`morphTo` / `morphOne`). The unified `workflow_nodes` table acts as the structural registry defining topological order, async flags, queue targets, and retry limits, while delegating its configuration payload to `configurable_type` and `configurable_id`. Specialized Eloquent models (`WebhookNodeConfig`, `ExtractDataNodeConfig`, `AsyncPdfNodeConfig`, `EmailNodeConfig`, `SlackNodeConfig`) encapsulate domain-specific schemas, JSON casts, and custom mutators. At runtime, the `WorkflowManager` eager-loads the polymorphic configuration and injects it directly into the instantiated node class via Laravel's Service Container, creating a strongly typed, maintainable, and schema-enforced configuration system.

## 4. Event Sourced Auditing & Queue Event Broadcasting
AutomataCLI treats state mutation as a first-class event stream. Every mutation to the `WorkflowPayload` is appended to the immutable `workflow_events` ledger, capturing the exact microsecond timestamp, node identifier, log level, delta summary, and full JSON before-and-after snapshots. This provides complete time-travel auditing: administrators can inspect the exact historical diff across every step of any run using `php artisan automata:inspect {id}`. To bridge the gap between asynchronous Laravel Queue workers (running on Redis or database drivers) and the live CLI console, heavy tasks implementing `AsyncNodeInterface` are dispatched via `ExecuteAsyncNodeJob`. The job records progress transitions (`NodeExecutionStarted`, `NodeExecutionCompleted`, `NodeExecutionFailed`), persists intermediate state snapshots to the database, and broadcasts updates. The CLI terminal runner utilizes an event-driven observer loop with Termwind and ANSI cursor repositioning to update the live Directed Acyclic Graph (DAG) topology, highlight the active worker queue (`high-priority`), display real-time attempt counters, and stream live scrolling audit logs without requiring terminal detachment.
